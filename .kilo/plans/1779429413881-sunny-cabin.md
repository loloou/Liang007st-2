# 项目整体评审与局部重绘完善计划

## 目标

对当前项目框架、主要业务逻辑和局部重绘功能做一次代码评审，并给出可执行的后续完善路线。当前处于计划模式，本计划只描述建议与实施步骤，不修改业务代码。

## 项目现状概览

- 技术栈：Electron 外壳 + Vite + React 18 + TypeScript + Tailwind CSS，前端为主，配置和历史主要落在 localStorage。
- 主流程：`App.tsx` 承担生图参数、模型配置弹窗、生成槽位、结果展示、历史、日志、弹窗调度等大量职责。
- API 层：`imageClient.ts` 负责 OpenAI/Gemini 生图，`inpaintClient.ts` 负责 OpenAI 兼容 `/v1/images/edits` 局部重绘。
- 结果层：`ResultPanel.tsx` 展示生成结果和右键菜单，已接入“局部重绘”入口。
- 配置层：`settings.ts` 的 `ImageModel` 已增加 `supportsInpaint`、`inpaintEndpoint`；`SettingsDialog.tsx` 已提供配置入口。
- 编辑器体系：存在 `editorStore.ts`、`types/editor.ts`、`editorPayload.ts`，支持更复杂的蒙版、文字、擦除、背景、裁剪、扩图 payload，但当前局部重绘弹窗未复用这套能力。

## 主要评审意见

### 1. 架构职责仍偏集中

- `App.tsx` 体量约数千行，仍聚合大量互不直接相关职责：生成任务、模型选择、设置弹窗、日志、历史、结果槽位、局部重绘回写、无限画布入口等。
- 已有 `generationStore.ts`，但 `App.tsx` 同时保留大量本地 state，形成“Zustand store + 组件本地状态”双轨状态源。长期看会增加同步成本和回归风险。
- 建议优先按业务域提取 hooks 或组件边界，而不是一次性重构：生成任务编排、模型选择/配置、历史/日志、局部重绘可以分阶段拆出。

### 2. 局部重绘 MVP 已可用，但与编辑器能力割裂

- 当前 `InpaintDialog.tsx` 自建 canvas mask 编辑器，只支持单层画笔/橡皮/反选/填满/数量/提示词。
- 代码库内已经存在 `editorStore.ts` 和 `editorPayload.ts`，支持更丰富的 mask layers、文本、擦除、参考图、扩图等编辑语义，但未进入当前局部重绘链路。
- 建议短期保留轻量弹窗，先补齐稳定性和可用性；中期把局部重绘与编辑器 payload 体系打通，避免两套编辑模型长期并存。

### 3. 局部重绘图像尺寸与 mask 尺寸存在潜在不一致

- `InpaintDialog.tsx` 会把加载图片按 `MAX_CANVAS_SIDE = 1400` 缩放后绘制，并导出同尺寸 mask。
- `inpaintImage` 请求中的 `size` 来自 App 当前的 `width/height`，不一定等于目标图片真实尺寸，也不一定等于 mask 导出尺寸。
- 若目标结果图来自历史、缩略图、不同尺寸模型或当前 UI 尺寸已变化，可能导致 API 端 image/mask/size 不匹配，进而失败或产生异常裁切。
- 建议优先在打开局部重绘时读取目标图真实尺寸，并将该尺寸作为弹窗和请求的单一来源；导出 mask 时也应匹配原图真实像素，或明确做等比缩放并同步请求尺寸。

### 4. 跨域与远程 URL 风险已有提示但缺少降级路径

- `inpaintClient.ts` 会通过 `fetch(url)` 把原图转成 Blob；远程 URL 受 CORS 影响时会失败。
- 当前错误提示可读，但用户只能“下载后重新导入或使用 base64 返回模型”。应用内没有直接的一键降级能力。
- Electron 环境具备通过主进程代理抓取远程图片的可能；浏览器模式可提示用户将图片转为 base64 或提供文件重导入入口。

### 5. 结果回写链路基本完整，但日志/历史元数据不够准确

- `handleInpaintComplete` 会生成缩略图、插入新 slot、更新 results、写日志和历史，这是正确方向。
- 日志中 `httpStatus` 固定为 200，未从 `GenerateResult` 传回真实值；失败日志目前主要停留在弹窗内，不进入详细日志。
- 历史记录未保存源图 id/source、mask 摘要、inpaint endpoint、原始尺寸等信息，后续追踪与复现能力不足。

### 6. API 客户端复用度和适配范围可提升

- `inpaintClient.ts` 和 `imageClient.ts` 有重复的 endpoint 构造、size snap、JSON 解析、HTML 判断、错误提取逻辑。
- 当前局部重绘强绑定 OpenAI 兼容 multipart `/v1/images/edits`。这是合理 MVP，但应在 UI 文案中明确“严格蒙版局部重绘只支持 OpenAI edit 兼容接口”。
- 兼容 API 可能使用不同字段，如 `image[]`、`mask_image`、`response_format`、`quality`、`background` 等。短期不建议盲目扩展，但应为模型级高级参数预留结构。

### 7. 测试覆盖不足

- 当前重点功能缺少针对 `inpaintClient` 的单元测试，尤其是 endpoint 构造、错误解析、返回图片提取、模型能力校验。
- Canvas 交互可不急于做完整 UI 自动化，但至少应把纯函数逻辑抽出测试。

## 局部重绘优先完善方案

### 第一阶段：稳定性与正确性修复

1. 统一目标图尺寸来源。
   - 打开 `InpaintDialog` 时加载目标图真实尺寸。
   - 弹窗标题和请求参数使用目标图尺寸，而不是 App 当前全局 `width/height`。
   - `onComplete` 写入 slot/history 时也使用这次局部重绘的实际尺寸。

2. 保证 image 与 mask 尺寸一致。
   - 保留 UI 显示缩放，但内部 mask 导出应以原图真实像素为准。
   - 若出于性能仍限制编辑画布尺寸，则请求 `image` 也应使用同尺寸 canvas 导出的 PNG Blob，而不是原始远程图片 Blob。
   - 推荐实现：在弹窗内维护 `workingWidth/workingHeight`，导出 `imageDataUrl` 与 `maskDataUrl` 都来自同一个工作画布尺寸，传给 `inpaintImage`。

3. 改善加载与生成状态。
   - 增加原图加载中状态，加载失败时禁用绘制和生成。
   - `handleGenerate` 使用 `try/finally`，防止未知异常导致按钮一直 running。
   - 生成期间禁用画笔、清空、反选、填满、数量选择等会改变请求输入的控件。

4. 提升 mask 判空性能。
   - 当前 `updateHasMask` 每次扫描整个 canvas 像素，图片较大时成本高。
   - 简化方案：绘制/填满时直接置 `hasMask=true`；清空置 false；橡皮或反选后再扫描。
   - 后续可维护 mask bounding box 或 dirty flag。

5. 回传真实请求元数据。
   - `InpaintDialog.onComplete` meta 增加 `httpStatus`、`requestBodyJson`、`sourceWidth`、`sourceHeight`。
   - `handleInpaintComplete` 日志使用真实 `httpStatus`，历史保存尺寸与 endpoint。

### 第二阶段：配置与 API 适配增强

1. 模型配置增加局部重绘说明和验证。
   - `supportsInpaint` 勾选旁补充提示：需要 OpenAI 兼容 `/v1/images/edits` multipart 接口。
   - 当全局/模型 `apiSpec` 是 Gemini 且未配置 `inpaintEndpoint` 时，在设置区直接给出弱提示。

2. 增加局部重绘连接测试。
   - 不真正发起昂贵生成，可先验证 endpoint 拼接与必要配置完整性。
   - 如果要真实测试，需用户确认并使用 1x1 或极小测试图，避免消耗额度。

3. 抽取 API 通用工具。
   - 把 `safeParseJson`、`isHtmlContent`、`extractErrorMessage`、OpenAI size snap 等抽到共享 util。
   - 降低 `imageClient.ts` 与 `inpaintClient.ts` 重复逻辑。

4. 预留模型级 inpaint 高级参数。
   - 可选字段：`responseFormat`、`quality`、`background`、`extraFieldsJson`。
   - 默认不展示复杂项，避免 UI 负担；高级折叠区中配置。

### 第三阶段：体验升级

1. 增加羽化/边缘柔化。
   - UI 增加 feather 半径。
   - 导出 mask 前对 alpha 做 blur 或边缘软化，减少重绘接缝。

2. 增加撤销/重做。
   - 简单实现可保存 mask canvas ImageData 栈。
   - 限制历史栈数量，例如 20 步，避免内存过高。

3. 增加视图缩放与拖拽平移。
   - 当前大图只适配显示，精修局部区域不够方便。
   - 支持滚轮缩放、空格/中键拖拽、适应窗口、100% 显示。

4. 增加源图重导入降级。
   - 当远程 URL CORS 失败时，弹窗内提供“选择本地原图继续”的入口。
   - Electron 模式后续可增加主进程代理下载，浏览器模式使用 file input。

5. 打通结果区与白板/编辑器。
   - 结果右键除“局部重绘”外，可增加“发送到编辑器/画布”。
   - 中期统一使用 `editorPayload.ts` 的结构表达 mask、擦除、文字、扩图等编辑任务。

## 建议实施顺序

1. 先修正尺寸一致性：目标图真实尺寸、工作画布尺寸、mask 导出尺寸、请求 size 四者统一。
2. 再补状态和异常：加载中、生成中禁用、try/finally、失败写日志。
3. 再补测试：`inpaintClient` endpoint、模型能力、错误解析、返回结构提取。
4. 再做体验项：羽化、撤销/重做、缩放平移。
5. 最后考虑架构整合：局部重绘弹窗与已有编辑器 payload/store 的合流。

## 验证建议

- 运行 `npm run type-check --workspace client`。
- 运行 `npm run lint --workspace client`。
- 运行 `npm run test --workspace client`。
- 手动验证：普通生图不受影响；结果图右键打开局部重绘；空 prompt、空 mask、未启用模型、Gemini 未配置 endpoint、远程图 CORS、成功返回 URL/base64 等场景都有明确反馈。

## 当前结论

局部重绘已经具备 MVP 入口和基本闭环，但最需要优先解决的是“目标图尺寸与 mask/request 尺寸一致性”和“失败/日志/历史元数据完整性”。整体架构上不建议立即大规模重构，应围绕局部重绘先做小步、可验证的修正，再逐步抽离 `App.tsx` 中的领域逻辑。
